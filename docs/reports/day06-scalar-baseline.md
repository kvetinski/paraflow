## What the evidence supports

1. The 1K fused pipeline fits a qualitatively cheaper per-record regime than
   the larger scenarios: 2.220 ns/record versus about 11.1–11.8 ns/record.
   Cache locality and fixed-cost effects are reasonable future hypotheses, but
   Day 6 has no hardware counters to attribute the cause.
2. The two controlled 64K fused medians differ by only 1.602 µs (about 0.22%).
   That difference is smaller than either scenario's MAD, so this run does not
   support a claim that hotspot distribution changes fused pipeline time.
3. Generation is the largest materialized boundary in every scenario, ranging
   from 30.50% to 67.93% of the sum of stage medians. Generation includes
   allocation, so allocation and data representation remain part of that
   hypothesis.
4. There is no universal dominant pipeline stage. The largest materialized
   pipeline boundary changes from aggregate at 1K to score, filter, and
   normalize across the larger scenarios.
5. Materialized pipeline passes cost 1.736×–2.378× the fused boundary in this
   run. The changed memory traffic, intermediate allocation, lost fusion, and
   observer boundaries are substantial enough that stage timings cannot be
   treated as an exact fused-loop decomposition.

## What the evidence does not support

- No parallel, SIMD, C++, ISPC, or GPU implementation was measured.
- No speedup, scalability, or core-utilization claim is possible.
- The stage profile does not prove the fused loop's hardware bottleneck.
- The run has no CPU affinity, NUMA binding, fixed-frequency policy, or
  hardware-counter attribution.
- The host appears to be a constrained environment with 9 visible logical
  CPUs; these values should not be generalized to other EPYC systems.
- One capture is portfolio evidence for method and hypotheses, not a universal
  performance characterization.

changed engine artifact, impossible timing conservation, incorrect paired
results, and an existing output path.
